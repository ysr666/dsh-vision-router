# v3.2.0-rc.0 — Host and Node compatibility retirement

**Historical aborted RC:** The rc.0 source tag exists, but npm publish failed before publication due an isolated release-workflow dependency error. No rc.0 npm tarball or GitHub Release was published. This file is retained solely for traceability; use the later verified RC instead.

**Pre-release publication status:** This document describes the 3.2.0-rc.0 candidate. It becomes a published opt-in prerelease **only after** the protected workflow verifies the exact npm `next` tarball, immutable GitHub prerelease, assets and provenance. A branch name or source tag alone is not a published upgrade. This RC does not replace npm stable `latest`.

- Minimum DSH 0.2.1-rc.5 and Node.js 24.9.0; currently recommended DSH 0.2.2-rc.1.
- DSH 0.1.x and 0.2.0, earlier 0.2.1 RCs and Node 22 are retired from this new DVR minor.
- DSH exclusively owns Host Connection authentication, API and trustedHosts; DVR private readiness bridge removed. A minimal webServer injection-order patch remains to preserve third-party RPC routes (Windows 405 regression).
- The modules/webServer ordering shim and DVR recompose guard remain until separately qualified.
- Retire the conflicting anonymous-user-id and storage-domain optional peer declarations, but **retain one optional DSH LLM peer** as a legacy refusal guard: official DSH 0.2.0-rc.2 ignores `engines.dsh` and otherwise incorrectly admits this new plugin. Supported rc5/rc1 Hosts gate by `engines.dsh`. Strict pnpm installs with either RC now pass without manually adding anonymous-user-id; `sharp` stays optional.
- Historic session, Settings and attachment data are not deleted; user-owned custom profile patches require separate review.
- **Host historical data caveat:** DSH 0.2.1-rc.5 may reject released v0 `subagent/descriptor` version-2 records, and 0.2.2-rc.1 still rejects unnormalized legacy `permission/preset.origin` records. These are separate upstream persistence-reader issues, not DVR migration fixes. Never assert full history compatibility without a target-Host read-only migration acceptance test; do not edit live session logs.
- Release workflow validation now uses Node 24.21 instead of retired Node 22. RC builds use npm `next` plus GitHub prerelease, not `latest`; unreviewed prerelease channels fail before immutable Git tagging. A green PR does not authorize a real publish.
- Verified on the candidate branch: 66 GitHub CI checks succeeded (two conditionally skipped; SHA c142fcb) for DSH rc5/rc1 and three OSes; an additional manually dispatched Linux/macOS/Windows 100MP stress matrix passed on the same commit. These are engineering results, not a published release.
- Existing profiles with manual Connection overrides must pass the new **`doctor --upgrade-preflight` (fail-closed on known profile blockers)** and the [read-only upgrade preflight](../architecture/dvr32-host-retirement.md#upgrade-preflight-and-safe-rollback-for-existing-profiles). This Host-retirement change itself does not rewrite user-owned profile patches, session, image or Settings stores.
- Windows real-Host reload probes return the expected HTTP statuses within a 5-second bound, with isolated 1.5–2.1-second tail latencies; UI bundle switch can render an intermediate state before a subsequent read converges. Neither is evidence of a persistent 404 or permanent inverse switch.
- **Opt-in release boundary:** Protected prerelease workflow and exact-commit verification are mandatory before any publication claim. Users must not auto-migrate existing Profiles or historical Session data to validate this RC. #792 screenshot root cause is still unconfirmed; upstream #806 stale-Fiber HMR remains open even though the DVR-specific 404 trigger is mitigated.
