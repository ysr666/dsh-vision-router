## Current root export topology

The current root is intentionally **not** curated during R0:

```text
package "."
  -> lib/public-entry.js
     -> export * from ../entry.js
        -> export * from ./index.js
           -> export * from ./lib/vision-resilience.js
```

Static export inventory at the R0 baseline:

- `index.js`: 101 direct named exports;
- `lib/vision-resilience.js`: 13 named exports re-exported by `index.js`;
- `entry.js`: 10 direct named exports plus the Core star export;
- estimated distinct package-root named surface after shadowing/deduplication: **122 names**.

This is an **inventory**, not an assertion that all 122 names are supported public API.
R7 must classify every root export as one of:

- `PLUGIN_CONTRACT`;
- `PUBLIC_SUPPORTED`;
- `PUBLIC_COMPAT`;
- `INTERNAL_ACCIDENTAL`;
- `TEST_ONLY`.

R0 must not reduce this surface before that classification because doing so would mix API
breakage with source/build migration.

## Production private-source policy

R0 installs a hard architectural rule:

> Production runtime code must not import or reference DSH package `src/*` entry points
> or `deepseek-harness/packages/*/src/*` monorepo implementation paths.

This applies to production entry points and `lib/**/*.js` now, and later to generated
runtime output from `src`.

The rule deliberately does **not** ban scripts/tests that inspect exact upstream source.
Files such as `scripts/dsh017-source-contract.mjs` are upstream compatibility
surveillance; they are allowed to inspect DSH implementation source because they do not
enter the npm production runtime graph.

## Compatibility baseline

2.3 closes with runtime Host support spanning the 0.1.5 train and exact 0.2.0-rc.2
evidence. 3.0 does not change that in R0.

Runtime Host compatibility and durable-data compatibility remain independent. A later
Host-floor raise cannot by itself remove replay, Settings/profile, Session, attachment,
route-identity, or historical image-ownership readers.

## R0 compatibility candidate: dsh-client-runtime

Current DVR still names `@deepseek-ai/dsh-client-runtime` in two places:

1. `package.json#dsh.client.inject`;
2. `lib/doctor-runtime.js#HOST_PACKAGES`.

At the audited DSH `0.2.0-rc.2` source baseline, repository search finds historical
references but no current package implementation that establishes this as a current
browser runtime package. DVR also has no identified `ctx.runtime` consumption.

Classification: **candidate stale Host/browser edge, not yet deletion-authorized**.

Removal requires real package/Host/browser evidence and must update both the manifest
and Doctor assumption together. R0 records the candidate; R6 owns the decision.

## R0 exit criteria

R0 is complete when:

- the 3.0 architecture plan exists in-repo;
- this contract ledger exists;
- the existing package/browser/support baselines remain unchanged;
- CI runs on the 3.0 development branch;
- production private DSH source references are forbidden by an executable architecture
  test;
- no runtime behavior, support floor, compatibility shim, release metadata, tag, npm
  package, or GitHub Release is changed.

The next phase is R1: establish a source/artifact boundary without mixing that move with
semantic refactors.
