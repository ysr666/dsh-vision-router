# DVR 3.0 R5 — Browser typed-source Go/No-Go

Status: **complete — production switch No-Go**

Baseline reviewed:

- branch: `3.0`
- experiment baseline: `8bda618ae7ebb2a5ee2ec9a2dd2f8868fb833a1c`
- browser hard gate: `262144` bytes
- canonical browser source: `src/lib/client.js`
- package artifact: `lib/client.js`

## Decision

DVR 3.0 will **not** convert the production browser client to TypeScript and will
not introduce a browser bundler merely to increase TypeScript coverage.

The existing JavaScript browser source remains canonical for 3.0.

This is a deliberate architecture decision, not deferred cleanup. The R5 success
criterion was never a `.ts` percentage; a production switch was allowed only if
typed generation stayed deterministic and transparent, preserved the supported DSH
loader model, and remained comfortably inside the frozen single-file review bound.

## Current size evidence

At the R5 checkpoint:

```text
src/lib/client.js  261672 bytes
lib/client.js      261672 bytes
hard gate          262144 bytes
headroom              472 bytes
```

The existing gate remains owned by
`tests/index-modularization.test.js` and is unchanged.

R5 does not:

- raise the 256 KiB gate;
- add minification as an architecture fix;
- add a browser bundler to hide source growth;
- inline source maps;
- merge the Host and Client TypeScript worlds.

## Whole-client migration

Whole-client TypeScript conversion is **No-Go**.

The browser entry is intentionally a self-contained DSH client-loader module built
by hand rather than a normal application bundle. Converting the whole file would
create a new build/runtime transformation at the most size-constrained package
boundary while providing little new ownership information: the mature browser
surface already has explicit presentation, Settings and remote-action boundaries.

With only 472 bytes of review headroom, this is the wrong place to spend architecture
budget merely to change the source language.

## Incremental embedded-owner experiment

R5 also tested the smallest credible typed migration rather than assuming that the
whole-client result applies to every browser owner.

The existing client contains one generated block:

```text
<generated:client-maintenance-actions>
```

Its source owner is `src/lib/client-maintenance-actions.js`; the deterministic
assembler is `scripts/sync-client-embedded-modules.mjs`.

A temporary, uncommitted TypeScript version of that owner was compiled under the
actual Client compiler world:

- `module: ESNext`
- `moduleResolution: Bundler`
- `lib: ES2024 + DOM + DOM.Iterable`
- `types: []`
- repository strict options including `noUncheckedIndexedAccess` and
  `exactOptionalPropertyTypes`

The owner could be made strict-type-correct without Node ambient types.

However, using the TypeScript-emitted function with the existing
`Function#toString()` deterministic inliner produced:

```text
current generated function     4099 bytes
TypeScript-emitted function    4133 bytes
delta                            +34 bytes

current client.js            261672 bytes
projected client.js          261706 bytes
projected headroom              438 bytes
```

The 34-byte increase by itself does not violate the hard gate, but it consumes
scarce browser review headroom for a low-risk owner.

## Build-lifecycle cost

The more important blocker is source/artifact ownership.

Today the sync script can import the canonical JavaScript owner directly from
`src/`. A TypeScript owner cannot be executed directly by the supported Node 22
repository lifecycle. A correct production switch would therefore need a separate
Client emit before synchronization, or would have to synchronize from a generated
`lib/` artifact.

That changes the lifecycle from the current simple relation:

```text
canonical JS owner
      -> deterministic inline sync
      -> canonical client.js
      -> package build
```

to a multi-stage relation such as:

```text
canonical TS owner
      -> Client compiler emit
      -> generated JS owner
      -> deterministic inline sync
      -> canonical client.js
      -> package build
```

This would require additional build ordering and reproducibility ownership for one
small browser helper. It is not justified by the coupling or lifecycle risk reduced.

Using the Host compiler to emit the browser owner was rejected: Client code must
continue to be checked in a browser-only world with `types: []`; Node ambient types
must not become an accidental browser source authority.

## Why this is not negative progress

The R5 experiment confirms that the current browser boundary is already the safer
architecture for 3.0:

- the 256 KiB review bound stays frozen;
- loader/runtime behavior stays transparent;
- no bundler or minifier becomes a new supply-chain/build owner;
- Host and Client compiler worlds stay separate;
- generated browser synchronization stays simple and deterministic;
- 3.0 effort remains focused on contracts where TypeScript materially reduces
  Host drift, lifecycle or ownership risk.

## Reopen conditions

R5 should be reopened only if at least one of these becomes true:

1. a real browser ownership extraction materially reduces `client.js` size before
   TypeScript is introduced;
2. the supported DSH browser/package contract provides a typed build path that does
   not require DVR to invent a new bundling lifecycle;
3. a browser owner develops a concrete contract/lifecycle risk large enough to
   justify a separate Client emit stage;
4. the resulting production artifact remains under the existing 262144-byte gate
   without minification or a gate increase.

A future desire for a higher TypeScript percentage is **not** a reopen condition.
