## 1. What 2.3.0 is now trying to achieve

2.3.0 is not a large feature release and is not a rewrite of the Vision Router architecture.

Its final architecture objective is:

> **make the current single-owner design safe under composition, current DSH Desktop/Host behavior, long-session edge cases, and future extraction — then remove only the mature-Core/browser glue whose replacement boundary is clearly better than the current one.**

The order matters. Correctness and integration come before further extraction.

The remaining phase has five priorities, in this order:

1. **Integrate the current v2.2.8 / Desktop / DSH 0.2-rc.2 mainline into the 2.3 branch.**
2. **Close confirmed correctness and lifecycle gaps**, especially Session event-feed overflow and asynchronous Core bootstrap settlement.
3. **Bring 2.3 compatibility evidence and developer baselines up to the current support reality.**
4. **Continue mature-Core and browser extraction only at stable ownership seams with measurable structural benefit.**
5. **Re-run an adversarial final audit on the integrated branch before release/version work begins.**

## 4. Frozen product and architecture decisions

These decisions remain fixed for the rest of 2.3.0.

### 4.1 Remote Settings is reminder-only

Remote Settings keeps the current product behavior:

- the browser may show a risk confirmation;
- `acceptedRisk` records acknowledgement of the warning flow;
- it is **not** a credential, authentication proof, administrator authorization, local-presence proof, challenge response or one-time secret;
- no 2.3 task adds a hidden second server-side confirmation gate;
- the actual capability boundary remains the remote mutable-field allow-list plus local-only fields.

The code now carries this product contract explicitly. Do not reinterpret historical `authorize*` RPC/function names as security-auth semantics.

### 4.2 Existing semantic owners stay authoritative

2.3 must not create a second owner for:

| Responsibility | Owner |
| --- | --- |
| routing/background authority | `vision-routing-authority.js` |
| routing evidence | `vision-routing-evidence.js` |
| planning/scoring | `vision-capability-router.js` |
| execution order | `vision-execution-order.js` |
| Session visual state/index | `session-vision-runtime.js` + state/index |
| managed artifacts | `vision-artifact-store.js` |
| Router-owned provider HTTP | `vision-provider-transport.js` |
| Host/product presentation state | server-side presentation/product boundaries |
| browser rendering | client/presentation layer |

No generic dependency-injection container, current-owner locator or Core-like service facade is introduced to reduce parameter plumbing.

### 4.3 Host-first network behavior remains authoritative

A blank DVR proxy continues to inherit Host/Undici network policy. Explicit `proxy` / `proxyHosts` remain supported Advanced product overrides. 2.3 does not re-own global network dispatch.

### 4.4 Compatibility retirement remains evidence-driven

No shim is removed merely because it is old or aesthetically awkward. The removal condition must be satisfied on the current integrated support matrix, including durable historical/session inputs where applicable.

The DSH Web activation overlays remain while exact supported/rc source contracts classify them as `shim-required`.

### 4.5 DVR 2.3 resets the supported Host floor and the default development Host

This is a deliberate 2.3 minor-release policy change, not an incidental consequence of dependency cleanup.

For DVR `2.3.0`:

- **Minimum supported DSH Host:** `0.1.5` train (earliest admitted release `0.1.5-rc.1`).
- **Default development Host:** exact `0.2.0-rc.2`.
- **Unsupported by DVR 2.3:** all DSH Host trains older than `0.1.5`, including the entire `0.1.0-rc.6/rc.7/rc.8` line and the intermediate 0.1.x pre-stable trains previously admitted for older DVR releases.
- The default development version is pinned exactly; it must not float through a caret range to a different rc without an explicit evidence update.
- Runtime compatibility remains capability-based. Raising the support floor does not authorize widespread version-string branching.

The policy distinction is intentional:

```text
public compatibility floor: DSH 0.1.5 train
ordinary 2.3 development:    0.2.0-rc.2 exact
older Host archaeology:      not part of the 2.3 supported Host matrix
```

Dropping an old Host does **not** automatically permit deleting compatibility code that protects durable data produced by older versions. Session logs, replay envelopes, persisted settings and other long-lived inputs are audited by data format/capability, not by the current Host version alone.

The 2.3 release notes, README/Doctor support messaging, peer admission and CI must all converge on this boundary before release.

## 6. Phase R1 — correctness hardening

Correctness fixes take priority over additional extraction.

### R1.1 Repair Session event-feed overflow without returning to full-history cloning

Status: **completed** by `669e445` (`fix(session): recover bounded event-feed overflow`).

Evidence: the original 257-event reproducer now repairs **257/257** with one exact recovery read; normal 256-event feed uses zero recovery reads; 400-event overflow recovers in capped 32-read batches; transient/unsupported readers retain dirty retry state; Session-focused suite **92/92**; full suite **1560 tests / 1559 pass / 1 skip / 0 fail**; remote gate `36589418063` success. Recovery stores only bounded seq ranges and uses `readSessionEvent()` — it does not return to whole-history cloning.

#### Confirmed defect

`session-vision-index.js` bounds each pending surface-repair map at 256 entries. When a 257th pending repair arrives, the oldest entry is currently deleted permanently.

A current-code reproducer with 257 pending guard-stop events yields:

```text
events:          257
repaired:        256
oldestRepaired:  false
```

The warning is emitted, but no recovery path restores the dropped repair. This trades bounded memory for silent durable-surface correctness loss.

#### Required design

Do **not** fix this by returning to repeated whole-session clones/snapshots; #527/#533 existed specifically to remove that failure mode.

Preferred recovery model:

```text
steady state
  session/event -> bounded pending repair map -> next pre-step repair

on overflow
  keep bounded fast-path map
  + mark this Session repair feed as dirty
  + remember the earliest/affected dropped repair range

next prepareDecision
  inspect current surface nodes
  recover missing repair events through Host-owned bounded SessionQuery.readEvent()
  in bounded batches
  apply only repairs that are still on the current surface
  keep dirty state until the affected current surface has been completely reconciled
  then return to event-feed steady state
```

The current `createSessionEventReader()` already uses `sessionQuery.readEvent({sessionId, seq})` and does not materialize the entire Session log. Prefer that exact-event capability for overflow healing. A whole-log `readSessionLog()` must not become the normal overflow repair path merely because it is convenient.

If exact-event recovery is unavailable on a compatibility Host, fail visibly and retain dirty/retry state rather than silently clearing the lost-repair condition.

#### Required tests

Cover:

- 257 pending guard repairs: all still-current repairs eventually complete;
- 257 pending tool-result repairs;
- dropped events removed from `surface.nodes` are not resurrected;
- recovery proceeds in bounded batches rather than unbounded allocations/reads;
- a transient `readEvent()` failure retries later;
- unsupported exact-event capability never silently marks the dirty repair complete;
- normal <=256 event-feed steady state performs zero extra SessionQuery reads;
- replacement events never re-enqueue themselves.

**Exit condition:** bounded memory no longer implies silent loss of a repair still present on the current Session surface.

### R1.2 Make Core schema-bootstrap completion follow the actual Core apply lifetime

Status: **completed** by `8fee12e` (`fix(runtime): settle Core bootstrap after async apply`).

The synchronous Core path remains synchronous, Promise-returning Core apply now keeps the schema-bootstrap window open until settlement, failure closes it exactly once, and post-Core installation follows the same settlement boundary.

#### Original latent gap

`runtime-composition.js` currently accepts a Promise-like return from `core.apply()`, but calls:

```text
coreVisionSurfaceRuntime.finishSchemaBootstrap()
```

immediately after invoking `core.apply()`, before a returned Promise settles.

Today the mature Core applies synchronously, so this is not a current production crash. However the composition contract is internally inconsistent: it claims async compatibility while ending the schema-bootstrap window synchronously.

#### Required design

Create one explicit Core-apply settlement path:

- synchronous return: finalize bootstrap exactly where it finalizes today;
- synchronous throw: close the bootstrap lifecycle and log/rethrow as today;
- Promise resolve: finalize bootstrap only after Core registration has completed;
- Promise reject: close the bootstrap lifecycle once, preserve the original rejection and bounded logging;
- post-Core installers that semantically require completed Core registration must run from the same settlement boundary.

Do not make all composition async solely to solve this. Preserve synchronous return behavior for the current Core.

#### Required tests

Use a stub Core for:

- synchronous success;
- synchronous throw;
- delayed Promise success with schema reads before/after settlement;
- delayed Promise rejection;
- exactly-once `finishSchemaBootstrap()`;
- wrapper/maintenance installation ordering relative to settlement.

**Exit condition:** the lifecycle behavior matches the return type the composition already claims to support.

The first pass proved that extraction is useful when the seam already has a stable owner (`maintenance-routes`, `desktop-screenshot-tool`, `public-config`). The second pass must use stricter acceptance criteria.

### R3.1 Extraction acceptance rule

A candidate moves out of `index.js` only when all are true:

1. it represents one coherent responsibility, not an arbitrary group of lines;
2. the resulting module has a narrower dependency set than the code had implicitly inside Core;
3. no module-global/current owner is introduced;
4. no Core-like facade or generic service locator is introduced;
5. the move can be behavior-preserving in its own commit;
6. the extracted contract can be tested directly without reconstructing most of Core;
7. composition/Core fan-out or product/lifecycle glue is measurably reduced.

If the extracted function needs a large bag of unrelated callbacks just to compile, the seam is not mature enough and remains in Core.

### R3.2 Primary candidate: diagnostics/product Web ownership still inside Core

Status: **completed** by `7015c2e` (`refactor(core): extract vision diagnostics routes`), with `4317d5f` preserving partial-LLM diagnostics behavior.

`index.js` previously directly owned Web registrations for:

- `/_dsh/vision-router/test-connection`;
- `/_dsh/vision-router/model-capabilities`.

These are product diagnostics/settings support, not visual inference algorithms.

2.3 should attempt to move them behind a narrow diagnostics owner **only if** the service boundary can be expressed cleanly, for example as explicit candidate/catalog/capability probes rather than passing most of Core into a route module.

Success means Core no longer owns WebServer registration for these endpoints.

That condition is now satisfied by `lib/vision-diagnostics-routes.js`. The extracted module receives three coherent diagnostics faces — connection candidates/probes, capability snapshot, and Host ownership state — rather than a Core facade.

Abort the extraction if the route module requires a broad Core facade or a dependency bag that simply reproduces `index.js` coupling elsewhere.

### R3.3 Secondary candidate: provider-call transport binding

Status: **rejected for 2.3 after dependency review**.

Core currently creates local helper closures to attach the explicit `providerTransport` to OpenAI/local/Anthropic calls.

A small typed/narrow provider-call binding module may be worthwhile if it:

- accepts only the explicit transport + concrete call functions;
- returns only the three transport-bound call operations;
- does not pretend to be Core;
- removes repeated transport option plumbing across Core/primitives;
- preserves direct helper callers without an implicit current transport.

This is explicitly different from the rejected historical `core-runtime-facade` approach.

If the module does not reduce dependency repetition in practice, leave the explicit call-site plumbing as-is.

That is the current result. The proposed module would only relocate three one-line closures. The underlying primitives still need explicit transport data for local/OpenAI/Anthropic and request paths, so the extraction would not eliminate or narrow those dependencies. Explicit plumbing therefore remains preferable to a cosmetic binding layer.

### R3.4 Do not make `core-primitives.js` line count a release criterion

`core-primitives.js` is still large, but 2.3 should not split it solely because it is ~3k lines.

A primitive group moves only when a clear data-plane owner emerges. OCR/image preprocessing/resource-governor code should remain together with its current owner until a move reduces coupling rather than adding interfaces.

**R3 exit condition:** met. Diagnostics/product Web ownership was cleanly extracted and the secondary transport-binding candidate was rejected with dependency evidence. The goal remains architectural clarity, not an arbitrary LOC target.
