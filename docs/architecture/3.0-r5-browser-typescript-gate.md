# DVR 3.0 R5 Browser TypeScript gate

> Status: **No-Go for monolithic Browser TypeScript migration**
>
> Audited branch: `3.0`
>
> Evidence checkpoint: `20723c368433fcc628a09fe168ca4a9d221e55e1`

## Decision

DVR 3.0 does **not** migrate `src/lib/client.js` wholesale to TypeScript at this stage.

This is not a rejection of TypeScript in Browser code. It is a boundary decision: the current Browser delivery topology does not provide enough architectural leverage to justify converting the monolith, and forcing the conversion would create new DTO/facade/type-maintenance debt without improving a stable ownership seam.

## Current bundle constraint

The canonical Browser source and delivered artifact are currently identical in size:

- `src/lib/client.js`: **261,672 bytes**
- `lib/client.js`: **261,672 bytes**
- existing single-file review bound: **262,144 bytes**
- remaining headroom: **472 bytes**

The existing `tests/index-modularization.test.js` gate continues to enforce the 256 KiB bound. R5 does not raise, weaken, or bypass it.

`pnpm client:check` is green at this checkpoint.

## Strict TypeScript characterization

A temporary, non-committed Client compiler spike added the existing `src/lib/client.js` to the current Client program with:

- `allowJs: true`
- `checkJs: true`
- inherited `strict: true`
- inherited `noUncheckedIndexedAccess`
- inherited `exactOptionalPropertyTypes`
- Client DOM libs
- `types: []`

The existing monolith produced **478 TypeScript diagnostics**.

Largest classes:

| Code | Count | Meaning |
| --- | ---: | --- |
| TS7006 | 258 | implicit-any parameters |
| TS2339 | 105 | dynamic/undeclared object properties |
| TS7005 | 60 | implicitly-any variables |
| TS7034 | 18 | variables whose array/object type cannot be inferred safely |
| TS7053 | 13 | dynamic indexed access |
| TS2367 | 13 | comparisons whose inferred domains do not overlap |

The first errors also expose real dynamic Browser/Host seams:

- `window.__ModuleLoader__`;
- injected `require()` values;
- React loaded through the Host module carrier;
- historical client attachment compatibility;
- mutable capability/state bags assembled at runtime.

Treating those surfaces as statically trustworthy would require either broad `any`, duplicated Host DTOs, or a large Browser facade. None reduces current ownership risk.

## Why this is a No-Go

A direct `.js -> .ts` conversion would currently optimize for file extension rather than architecture.

It would tend to require one or more of the following, all rejected for 3.0:

- a large DVR Browser/Host facade;
- copied Host client DTOs;
- broad `any` or assertion-heavy adapters;
- a new bundler/transpilation layer solely to preserve the existing single-file delivery shape;
- generated TypeScript source embedded back into `client.js`;
- raising the 256 KiB review bound;
- minification as an architectural escape hatch.

The current Client compiler world therefore remains intentionally separate and narrow. Host TypeScript migration must not leak Node ambient types into it.

## Existing source ownership remains valid

Browser behavior is already partially source-owned outside the monolith where a stable owner exists. For example, maintenance actions are authored in `client-maintenance-actions.js` and deterministically embedded into `client.js`; `pnpm client:check` verifies synchronization.

That pattern should not be mechanically converted to TypeScript either. In particular, a function serialized with `Function#toString()` cannot safely carry TypeScript-only syntax into the delivered browser source.

## Re-open conditions

R5 Browser TypeScript should be reconsidered only when at least one of these becomes true:

1. a substantial Browser responsibility gains an independent stable owner that can be typed without copying the monolith's dynamic Host surface;
2. DSH exposes a public typed Client module/context contract that removes the need for DVR-owned facades;
3. the Browser delivery topology gains an official build/bundle seam where TypeScript can compile without changing runtime ownership or weakening the size gate;
4. source extraction creates enough review headroom that a typed owner can be introduced without hiding growth through minification;
5. a concrete Browser bug class is shown to be prevented by a narrow type boundary.

## Invariants retained

- no increase to the 262,144-byte client bound;
- no Node globals in the Client TypeScript program;
- no production dependency on DSH private `src/*` paths;
- no broad Host facade;
- no repository-wide Browser TypeScript rewrite;
- no minification-based architecture fix;
- runtime validation remains authoritative for dynamic Host/client data.

R5 therefore closes as **No-Go for monolithic migration, open for future owner-by-owner typed extraction when a real seam appears**.
