# DVR 2.3.0 final architecture audit

> **Superseded as a final decision / retained as a first-pass audit snapshot.** A later adversarial review reopened 2.3.0 after finding a Session event-feed overflow correctness hole, unresolved original audit items, and a parallel v2.2.8/Desktop/DSH 0.2-rc.2 mainline that must be integrated. The active plan is `2.3.0-reopened-plan.md`.

Code baseline: `2.3.0@0284bdc77fd4ab0af96a9f14300d6caec9059938`.

Architecture gate: GitHub Actions run `36578577418` (`2.3 Critical Architecture Gate`) — success on the exact code baseline above.

This audit closes the 2.3.0 **composition hardening + compatibility retirement + mature-Core extraction** phase. It does not declare the repository fully modular or compatibility-free. The acceptance criterion is narrower: reduce hidden composition coupling and transitional ownership without changing the established semantic owners.

### Relationship to DSH Desktop compatibility work

`completed` in this audit means the 2.3 branch satisfies the workstream exit condition; it does **not** mean every enabling hardening change was first authored during this phase.

The `2.3.0` branch was cut from `v2.2.7@74e3f01`. That baseline already inherited Desktop/new-Host compatibility work, including `58d2f21` (`fix(settings): recognize official Desktop origin`) and the earlier DSH 0.1.7 Settings/Session/Web lifecycle hardening. Those changes are prerequisites inherited by 2.3, not new 2.3 accomplishments.

After the branch cut, `main` also evolved in parallel through Desktop compatibility work such as `b1bd5ec` (`fix(desktop): unify client injection carriers`) and `2c4c57d` (`fix(desktop): release stale vision tool masks`). Those commits are not ancestors of the audited 2.3 branch and are not patch-equivalent to the 2.3 commits. They must be reconciled explicitly before integration rather than being double-counted as work performed by this phase.

Accordingly, 2.3 should be read as **inherit + harden + make ownership explicit + retire satisfied transitional seams**, not as a claim that every surrounding Desktop/Host compatibility mechanism originated here.

## 2. Workstream A — composition hardening

### A1. Runtime i18n fetch lifecycle — completed

`runtime-i18n-boundary.js` no longer publishes or restores its wrapper through direct `globalThis.fetch = ...` assignment. It uses the same descriptor-safe `captureFetchDelegate()` / `installFetchWrapper()` lifecycle as the pi-ai wire and legacy proxy boundaries.

The original Host-accessor recursion is permanently covered. A production scan at the final baseline finds no direct DVR `globalThis.fetch` assignment.

### A2. Cross-boundary fetch composition matrix — completed

The matrix now covers:

- wire only;
- i18n only;
- proxy only;
- every production-relevant two-wrapper combination;
- the full `wire -> i18n -> proxy` chain;
- Host accessor installation before and after DVR wrappers;
- non-LIFO cleanup;
- live Host middleware replacement/removal;
- later Host fetch replacement;
- simultaneous i18n prompt localization, wire-field/header correction and scoped proxy dispatch.

The matrix is part of the default/compat test ownership and the 2.3 critical gate.

### A3. Runtime composition phases — completed

`applyVisionRuntimeComposition()` is now a narrow five-phase composition entry:

```text
installHostAndSecurityBoundaries
  -> createRuntimeOwners
  -> installRoutingAndHostProducts
  -> installExecutionBoundaries
  -> applyMatureCoreBridge
```

The refactor intentionally preserved the historical installer order. No semantic authority moved into the phase functions.

The raw import fan-out remains high — 44 direct module dependencies at the final baseline versus 43 on the 2.2.7 baseline — because composition still owns construction of the product graph. The improvement is explicit lifecycle grouping and dependency handoff, not a cosmetic fan-out reduction.

### A4. 2.3 critical architecture gate — completed

The branch-local gate runs:

- Node 22 and Node 24 full regression;
- composition/architecture/security property contracts;
- package smoke;
- an isolated current Host `0.1.5-rc.3` contract fixture;
- one aggregated `critical-gate` result.

It runs on `2.3.0` pushes and manual dispatch. It does not change `main` branch protection by itself.

Final exact run: `36578577418` — success.

## 3. Workstream B — compatibility retirement

### B1. VisionProviderTransport registry — retired

The former process/profile carrier is gone:

- no module-level `installed[]`;
- no `installVisionProviderTransport()`;
- no `currentVisionProviderTransport()`;
- no replacement `current transport` locator.

The dependency is explicit:

```text
public-entry
  -> internal runtime dependency
  -> mature Core call sites
  -> http-compat / catalog-corrections
```

Direct/unit helper fallbacks remain available where they were already part of the helper contract. Concurrent explicit transports are covered so one runtime cannot steal another runtime's transport by installation order.

### B2–B4. Retained compatibility — reconciled, not force-deleted

The current inventory contains:

| `retain-host-gap` | 6 |
| `product-compat` | 5 |
| `retire-ready` | 0 |
| `historical-only` | 0 |

The detailed reasons/removal conditions live in `compat-inventory.md` and the 2.3 review in `2.3.0-compat-retirement.md`.

Notably:

- DSH `modules -> webServer` and `connection -> webServer` overlays remain because exact admitted upstream evidence is still `shim-required`;
- `proxy` / `proxyHosts` remain supported Advanced product overrides;
- Remote Settings keeps the frozen 2.3 product decision: its risk confirmation is a **reminder/acknowledgement only**, not server-side authentication or a second validation gate.

## 4. Workstream C — mature-Core extraction

2.3.0 followed the rule “extract stable ownership seams, not lines”. It deliberately did not attempt to explode the mature Core into many helpers.

### C1. Public Config construction — completed

`entry.js` no longer performs the product Config/default mutation inline. `lib/public-config.js` owns explicit public schema/default composition while preserving the mature Core schema identity and existing public behavior.

`entry.js` changed from 80 lines at the 2.2.7 baseline to 38 lines at the final code baseline.

### C2. Product/maintenance Web routes — completed

Update/self-update and related maintenance route ownership moved out of `index.js` into `lib/maintenance-routes.js`, installed through runtime composition and still subject to the existing Web capability/authentication boundary.

### C3. Stable tool extraction — deliberately partial

The desktop screenshot tool implementation moved to `lib/desktop-screenshot-tool.js` behind a narrow construction seam. The move preserves the existing screenshot source/runtime authority and platform compatibility behavior.

Other candidate groups such as OCR/image preprocessing were **not** extracted merely to reduce file size. At this phase they still share enough mature-Core execution/resource state that another extraction would add interfaces without eliminating an owner or known defect. They remain valid future extraction candidates when a narrower stable contract exists.

### C4. Browser current-product source modularization — completed for maintenance actions

Update check, self-update, connection test, screenshot-permission probe and log-folder actions now have a real source owner in `lib/client-maintenance-actions.js`, independent of React, Settings, routing and Host context.

DSH still consumes one injected `lib/client.js` bundle. Therefore a deterministic sync script embeds the source-owned function into the delivered bundle and `client:check`/tests reject drift.

This is **source modularization**, not physical bundle splitting. `client.js` is 4914 lines at the final baseline versus 4858 on 2.2.7; 2.3.0 must not claim the shipping browser bundle became smaller.

## 6. Global/process-state adversarial review

Repository-wide final scans found:

- no production `currentVisionProviderTransport` / `installVisionProviderTransport`;
- no module-level transport `installed[]` registry;
- no direct DVR assignment to `globalThis.fetch`;
- no ESM import cycle.

Remaining module-level state is composed of scoped/capability mechanisms such as WeakMap/WeakSet wrappers, AsyncLocalStorage request/turn scopes, bounded artifact/resource state and lazy module caches (for example Sharp loading). These are not a replacement current-owner locator.

The long-term Architecture Closure tests continue to forbid hidden module-global `current*` semantic owners and unregistered `installed[]` runtime registries.

## 8. Retained debt after 2.3.0

The phase closes with explicit retained debt rather than a blanket purity claim:

1. **Mature Core remains large.** `index.js` is 5083 lines with fan-out 31. Future extraction should continue only at stable owner seams.
2. **`core-primitives.js` remains a large shared foundation.** At 3033 lines/fan-out 26 it deserves future decomposition only when responsibility boundaries are clearer than shared primitive reuse.
3. **The shipping browser bundle remains monolithic.** Source ownership improved, but the Host delivery contract still embeds current-product code into one `client.js` file.
4. **Composition remains the highest fan-out module.** Five explicit phases make lifecycle coupling inspectable, but new installers should be challenged before adding more dependencies to the root.
5. **Eleven compatibility seams remain intentionally supported.** None currently satisfies its documented removal condition.
6. **DSH Web activation overlays remain externally blocked on upstream ownership.** Source-contract watchers must continue to classify `shim-required`, `retire-ready` or dangerous drift.

None of these retained items establishes a second semantic owner or a current 2.3 release blocker.

## 9. Exit decision

The 2.3.0 architecture phase is **complete** at the audited code baseline.

The achieved state is:

```text
2.2.7
  correct single owners
  + substantial compatibility/composition surface
  + mature Core product/lifecycle glue

2.3.0 architecture branch
  same semantic owners
  + descriptor-safe fetch composition
  + explicit five-phase runtime construction
  + branch-level critical architecture gate
  + explicit provider transport dependency
  + compatibility inventory with no speculative deletions
  + public Config / maintenance routes / desktop screenshot source extracted
  + source-owned browser maintenance actions with deterministic bundle sync
```

The next work should be release/integration preparation or a separately planned extraction phase, not additional opportunistic 2.3 refactoring.
