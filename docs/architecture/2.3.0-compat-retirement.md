# DVR 2.3.0 compatibility retirement review

> **R2.3 re-audit complete.** The original review predates the v2.2.8 / DSH 0.2.0-rc.2 / shared Desktop client-carrier line. The reopened audit retired every seam proven to exist only for a pre-`0.1.5` Host and reclassified the remaining seams against current-Host, durable-data, product, or platform evidence.

Review baseline: `2.3.0@d808014` after explicit `VisionProviderTransport` plumbing.

This review records Workstream B of the 2.3.0 architecture plan. A compatibility seam is not removed merely because it is old or awkward; deletion requires its existing removal condition to be satisfied by current Host/product evidence.

## Result

The process/profile `VisionProviderTransport` registry, the pre-floor Android/no-batch attachment fallback, and the pre-floor DeepSeek provider reconstruction path are retired. No remaining retained compatibility seam is presently classified `retire-ready` or `historical-only`.

| State | Count | Meaning in 2.3.0 |
| --- | ---: | --- |
| `retain-host-gap` | 6 | A supported/admitted Host still lacks the native seam needed to remove it. |
| `product-compat` | 4 | DVR intentionally retains provider, persisted-history, platform, or voluntary legacy compatibility independent of a current Host defect. |
| `retire-ready` | 0 | No remaining seam has met its removal condition. |
| `historical-only` | 0 | No retained seam is dead production code awaiting deletion. |

The canonical per-file classifications live in `compat-inventory.md` and are checked by `compat-inventory-completeness.test.js`.

## B1 — retired provider transport registry

The former module-level `installed[]`, `installVisionProviderTransport()` and `currentVisionProviderTransport()` carrier has been deleted. The production dependency path is now explicit:

```text
public-entry creates VisionProviderTransport
  -> entry internal runtime argument
  -> runtime-composition Core runtime dependency
  -> mature Core call sites
  -> http-compat / catalog-corrections options
```

Direct/unit helper callers retain their historical fallback behavior when no explicit transport is supplied. Two concurrent explicit transports are regression-tested to remain isolated, so one runtime can no longer steal another runtime's provider transport by being installed last.

Architecture Closure now forbids every module-global `installed[]` runtime registry rather than allowing a provider-transport exception.

## R2.3-C — retired rc.7-era public compatibility aliases

The transitional public aliases `isRc7ContractRuntime`, `protectRc7ProviderOwnership`, and `installRc7SettingsCompatibility` are removed from both `entry.js` and `lib/dsh-contract-compat.js`.

Repository-wide reachability review found no production consumer: the names existed only as public re-exports plus tests asserting that each alias equaled its capability-named replacement. DVR 2.3's support floor is now the continuous DSH 0.1.5+ line, so retaining rc.7-labelled API aliases would preserve only implementation archaeology rather than supported behavior.

The capability-named APIs remain authoritative:

- `hasBatchAttachmentContract`;
- `protectHostProviderOwnership`;
- `installHostSettingsCompatibility`.

This retirement changes no runtime behavior and intentionally shrinks the 2.3 public compatibility surface.

## R2.3-D — supported-window retained-seam verdict

After the three concrete retirements above, the remaining seams were re-audited against minimum `0.1.5-rc.1`, current `0.1.5-rc.3`, mid-train `0.1.7-rc.2`, and exact `0.2.0-rc.2` evidence.

The review stops deleting code at this point because every remaining seam has a reachable non-pre-floor reason:

- `dsh-contract-compat.js`: supported Settings generations still differ, SessionQuery readers remain capability-scoped, and historical attachment-policy overlays are durable profile data that can survive a Host upgrade;
- `adapter-update-coalescer.js`: DVR-owned adapters remain plain/duck-typed objects and still require current Host base-contract normalization plus bounded synchronous reconciliation;
- `settings-client-rc8-lifecycle.js`: despite its historical name, immutable 0.1.5-rc.1 through 0.2.0-rc.2 sources still replace the live module loader during `create()`; the current permission/risk wrappers must therefore reattach. Renaming/source modularization belongs to R4;
- `pi-ai-bridge-wire-compat.js`: current pi-ai carries generic `sessionId` but does not yet emit OpenCode Go's required `x-opencode-session`;
- replay, proxy, legacy Core visual-policy, HTTP, Tesseract and AbortSignal seams remain durable-data, explicit product, or runtime/platform compatibility rather than pre-floor Host support.

The normative exact-source matrix now excludes pre-floor `0.1.5-alpha.2`. That immutable Host may remain in a separately labelled browser surveillance workflow, but it is not peer-admitted or counted as DVR 2.3 support evidence.

This is the final R2.3 exit state. The renamed compatibility suite, minimum/current contracts, exact supported-source matrix and aggregate 2.3 gate are green. Final evidence:

- exact supported 0.1.x source matrix: run `36659179011`;
- minimum/current Host contract: run `36660877445`;
- aggregate 2.3 gate: run `36660877636`, including Node 22/24, current `0.1.5-rc.3`, exact rc.2 source on three OSes, Chromium, Windows Desktop 22/24, macOS Desktop lifecycle and final `critical-gate`.


## B2 — retained seam classification

### `retain-host-gap`

- `dsh-contract-compat.js` — attachment/settings/provider contracts still vary across admitted Host generations.
- `adapter-update-coalescer.js` — adapter contract/event ordering compatibility remains required by supported Host behavior.
- `pi-ai-bridge-wire-compat.js` — direct image bridge wire facts and OpenCode session affinity are not yet fully native on every supported path.
- `settings-client-rc8-lifecycle.js` — browser settings lifecycle still differs across the support window.
- `legacy-global-proxy-boundary.js` — Host-owned visual adapters still expose no DVR-scoped request/dispatcher parameter for the supported explicit proxy override.
- `legacy-core-vision-policy-bridge.js` — the Host still lacks both native session-memory rewrite and durable current-turn attachment-reference seams needed by the two retained behaviors.

### `product-compat`

- `replay-envelope-v2-compat.js` — persisted historical sessions are product data compatibility, not merely a currently running Host-version branch.
- `http-compat.js` — provider/model wire quirks are an intentional provider compatibility layer.
- `tesseract-exec-compat.js` — Node/platform child-process and Windows DPI behavior is a platform compatibility concern.
- `abort-signal-compat.js` — partial Host/bridge JS realms remain a runtime compatibility concern; native helpers are never replaced when present.

## R2.3-A — retired Android/no-batch attachment fallback

The reopened support-window audit retires `lib/android-attachment-compat.js` and `attachmentContextForContract()`.

This is a reachability deletion, not an Android product-policy withdrawal. The retired wrapper could run only when the Host attachment service lacked `saveImages()`. Every immutable Host line spanning the DVR 2.3 support/evidence window already exposes the batch contract:

- `dsh-v0.1.5-rc.1` — `183f08e9c6dde7e36cd2318eaee70b0da08fb35e`;
- `dsh-v0.1.5-rc.3` — `a4c74a91e06b00fe0b0937bde982170c526cc842`;
- `dsh-v0.1.6-alpha.1` — `0a15e36e7f82b6ed45af6fa9759f29b40dcd965d`;
- `dsh-v0.1.7-rc.2` — `477b4f420553e8a52c2fbccc464d7561b239c443`;
- `dsh-v0.2.0-rc.2` — `639ed015397290b3745d163aafe02ffee4aa3f84`.

The former helper also installed the read-only Host capability diagnostics route. That side effect is preserved explicitly in `runtime-composition.js` through `installDshHostCapabilityDiagnostics(settingsCtx)`, and the P3 composition contract locks its position before the tool/runtime boundaries.

The fallback stored only bounded process-local transient image bytes, so no durable Session/profile/config input depends on it. Removing it therefore changes no supported Host behavior and removes no durable-data reader.

## R2.3-B — retired legacy DeepSeek provider reconstruction

DVR 2.3 no longer rebuilds a missing `deepseek-official` provider, registers the hidden `deepseek-official-native` surrogate, waits on the historical 2-second keep-alive settle window, or reconstructs `@deepseek-ai/dsh-llm-deepseek` from plugin-owned settings/credentials.

The deletion follows the same immutable Host evidence used by R2.3-A: every supported Host generation from `0.1.5-rc.1` forward owns the batch attachment contract and therefore the official DeepSeek request-local attachment/file/image-access lifecycle. Reconstructing that adapter inside DVR would create a partial second owner and is no longer an allowed supported-Host fallback.

The persisted `stealth` setting remains readable so existing profiles continue to load; under DVR 2.3 it does not grant provider-takeover authority. A missing official row is reported as `host-owned-official-unavailable` and users are directed to re-enable `llm-deepseek`.

Durable-data compatibility is intentionally separate from production creation. `replay-delegation.js`, the scoped proxy boundary and Host-ownership guard may continue to recognize the historical `deepseek-official-native` identifier so old Session/replay/config inputs remain interpretable. R2.3-B removes the code that **creates** the route, not the code that safely understands historical evidence.

## B3 — DSH Web activation overlays remain required

The exact DSH `0.2.0-rc.1` evidence recorded in `dsh-support-window.md` still has:

- the official `modules` row without a `webServer` activation dependency;
- the official `connection` row owning `webRuntime` but not `webServer`.

Therefore the DVR `modules -> webServer` and `connection -> webServer` overlays remain `shim-required`. Existing source-contract classifiers intentionally fail with `retire-ready` when upstream begins owning these dependencies; 2.3.0 does not pre-empt that signal.

## B4 — legacy proxy compatibility remains narrow

`proxy` / `proxyHosts` remain supported, non-deprecated Advanced overrides. The compatibility boundary is retained because Host-owned visual adapter requests still cannot receive the DVR override explicitly.

The only unscoped fallback is the documented persisted/manual legacy state:

```text
routing === true
chainRoute === ''
```

Whitespace, a configured chain route, routing disabled, Router-owned direct HTTP, and ordinary Host traffic do not obtain this unscoped authority. `legacy-global-proxy-boundary.test.js` locks this reachability and the scoped/concurrent isolation behavior.

No proxy product-policy change is part of 2.3.0.

## Remote Settings is not a compatibility-retirement target

Remote Settings keeps the frozen 2.3.0 product decision: the risk confirmation is a reminder/acknowledgement, not a server-side authentication or validation gate. Workstream B does not reclassify or strengthen that behavior.

## B exit decision

Workstream B plus reopened R2.3 currently records three real retirements (the provider transport registry, the Android/no-batch attachment fallback, and legacy DeepSeek provider reconstruction) and no speculative shim deletion. Mature-Core extraction may proceed while the remaining compatibility inventory stays capability-detected and independently removable when its recorded conditions become true.
