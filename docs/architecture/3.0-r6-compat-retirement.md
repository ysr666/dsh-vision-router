# DVR 3.0 R6 — Compatibility retirement / Host-floor re-audit

Status: **complete — one stale package edge retired; Host floor unchanged**

Baseline:

- DVR branch: `3.0`
- DSH exact source: `deepseek-ai/deepseek-harness@639ed015397290b3745d163aafe02ffee4aa3f84`
- DSH version: `0.2.0-rc.2`
- public DVR Host window remains:
  - `>=0.1.5-rc.1 <0.2.0-0`
  - or `>=0.2.0-rc.2 <0.3.0-0`

R6 re-runs compatibility removal conditions. It does **not** treat age, a TypeScript
migration, or the current development pin as evidence that a compatibility owner is dead.

Durable user-data compatibility remains independent of the runtime Host floor.

## Result

R6 found one real stale package-graph edge:

```text
@deepseek-ai/dsh-client-runtime
```

It was retired from both:

- `package.json#dsh.client.inject`;
- Doctor's Host-package diagnostic inventory.

No documented runtime compatibility seam met its removal condition, and the public Host
floor is not raised.

## Retired: stale dsh-client-runtime client injection

### Evidence

The exact DSH `0.2.0-rc.2` client architecture has no
`@deepseek-ai/dsh-client-runtime` package.

Repository review also found no DVR production consumer of a `ctx.runtime` or equivalent
client-runtime service. The only remaining DVR references before retirement were:

1. `package.json#dsh.client.inject`;
2. Doctor's diagnostic package list.

This matters because current DSH does not define `dsh.client.inject` as an optional
capability hint. Its client-module contract describes inject entries as package dependency
edges: injected package factories must arrive before the consuming row materializes, and
Cordis uses the same edges for entry composition.

A package name that no longer exists therefore has no supported ownership role as a
compatibility placeholder.

### Retirement

R6 removes the stale row rather than replacing it with another guessed package.

The retained client inject list continues to use only the existing DVR-declared package
edges; no unrelated browser dependency is changed.

Doctor also stops reporting `@deepseek-ai/dsh-client-runtime` as a Host package. Keeping
the diagnostic after removing the graph edge would have produced false missing-package
evidence.

A regression gate in `tests/manifest-dependencies.test.js` now forbids the package name
from returning to either surface.

### Validation

After retirement:

- canonical build succeeded;
- generated-artifact reproducibility succeeded;
- Host TypeScript program succeeded;
- Client TypeScript program succeeded;
- manifest, Doctor, browser-client and DSH-compatibility targeted tests passed
  `193/193`.

## Host floor: KEEP

R6 does not raise the minimum Host from `0.1.5-rc.1`.

A Host-floor increase requires evidence that dropping the admitted Host generation removes
real compatibility complexity without conflating runtime compatibility with persisted data.
That condition is not met.

Several retained seams remain reachable for current product/platform reasons even if older
Hosts were removed, while other seams still span genuine lifecycle differences inside the
declared support window.

Raising the floor would therefore reduce support without producing the architectural
simplification required by the 3.0 plan.

## Retained: DSH Web modules -> webServer overlay

Verdict: **KEEP — shim-required**

Exact `0.2.0-rc.2` source still declares:

```yaml
- id: modules
  name: '@deepseek-ai/dsh-client-modules'
```

with no activation `inject` field.

The existing retirement classifier therefore remains in `shim-required`, not
`retire-ready`.

DVR must keep the overlay until an admitted Host's official modules row owns
`webServer` itself.

## Retained: DSH Web connection -> webServer overlay

Verdict: **KEEP — shim-required**

Exact `0.2.0-rc.2` source still declares:

```yaml
- id: connection
  name: '@deepseek-ai/dsh-client-connection'
  inject: [webRuntime]
```

The official row still does not own `webServer`.

The existing classifier correctly remains `shim-required`. If upstream later adds
`webServer`, the surveillance gate is already designed to change to
`retire-ready` and force an explicit DVR retirement before that Host train is admitted.

## Retained: pi-ai / OpenCode Go session-affinity projection

Verdict: **KEEP — Host gap remains**

Exact DSH `0.2.0-rc.2` `PiAiAdapter` propagates the Harness session identity into
pi-ai:

```text
GenerateOptions.sessionId
  -> streamSimple(..., { sessionId: String(options.sessionId) })
```

but the current DSH source contains no `x-opencode-session` carrier.

That is precisely the documented removal condition for DVR's scoped OpenCode Go wire
projection: generic `sessionId` propagation is not equivalent to the endpoint-required
header.

The DVR rule remains narrowly scoped to an active Vision Router affinity scope and the
official `https://opencode.ai/zen/go...` endpoint. It must not be retired until the
native header is emitted on every supported path.

## Retained compatibility inventory

The remaining normative seams in `compat-inventory.md` continue to satisfy at least one
current removal blocker.

### Host-gap owners

- `dsh-contract-compat` — Settings lifecycle still spans admitted Host generations;
  durable historical attachment-policy overlays are a separate data-compatibility reason.
- `adapter-update-coalescer` — DVR still owns duck-typed adapters whose Host base
  contracts and synchronous topology updates require normalization/coalescing.
- `pi-ai-bridge-wire-compat` — native OpenCode affinity remains absent as proved above;
  legacy direct bridge removal is independently gated.
- `settings-client-loader-lifecycle` — the supported browser module lifecycle still
  requires post-create reattachment across the declared Host window.
- `legacy-global-proxy-boundary` — explicit DVR proxy override for Host-owned visual
  adapters remains a supported product capability with no scoped Host dispatcher seam.
- `legacy-core-vision-policy-bridge` — the Host still lacks the two exact pre-step
  capabilities recorded by the inventory; the 3.0 typed Core-surface work did not create
  an upstream substitute.

### Product / durable-data / platform owners

These are not Host-floor retirement candidates:

- `replay-envelope-v2-compat` — durable replay data;
- `http-compat` — evidenced provider wire behavior;
- `tesseract-exec-compat` — Node/process and Windows DPI behavior;
- `abort-signal-compat` — partial runtime-realm capability compatibility.

Deleting any of these merely because the current Host pin is `0.2.0-rc.2` would mix
independent compatibility domains.
