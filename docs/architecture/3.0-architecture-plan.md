# DVR 3.0 architecture plan

Status: **complete — R9 final audit passed**

Baseline:

- DVR `main@c61802dfc591410ba328b7f4c8f983b0e3d5f447`
- DSH `deepseek-ai/deepseek-harness@639ed015397290b3745d163aafe02ffee4aa3f84` (`0.2.0-rc.2`)
- 3.0 development branch: `3.0`
- implementation closure checkpoint: `1e331b1b8f8ea74a5cd38a1347f4e0bd13ef9ef9`
- final audit: `docs/architecture/3.0-r9-final-audit.md`

3.0 is **typed architecture consolidation**, not a repository-wide TypeScript rewrite.
The success criterion is that changes to DSH contracts, lifecycle ownership, Settings,
Session, provider contracts, and public package boundaries fail loudly at the nearest
compiler/runtime/package gate. The percentage of files ending in `.ts` is not a goal.

## Invariants inherited from 2.3

3.0 must preserve the semantic owners established by 2.3:

| Responsibility | Owner |
| --- | --- |
| routing/background authority | `lib/vision-routing-authority.js` |
| routing evidence | `lib/vision-routing-evidence.js` |
| planning/scoring | `lib/vision-capability-router.js` |
| execution order | `lib/vision-execution-order.js` |
| Session visual state/index | Session runtime/state/index owners |
| managed artifacts | `lib/vision-artifact-store.js` |
| DVR-owned provider HTTP | explicit `VisionProviderTransport` instance |
| Host/product projection | server presentation boundaries |
| browser rendering | client/presentation layer |

High fan-out in `runtime-composition` is expected for a composition root and is not
by itself an extraction target. Core extraction requires a stable semantic owner, not
a line-count or import-count justification.

## Required architecture direction

```text
DSH public contracts
        |
        v
narrow Host boundaries
        |
        v
DVR domain types
        |
        v
Authority -> Evidence -> Planner -> Execution
        |                       |
        +------ composition ----+
                  |
                  v
             mature core
```

Host types and DVR domain types must not become one giant interface graph.

## Source/build target

The target package model is:

```text
canonical source                    generated package artifact
src/**/*.ts / transitional .js  -> lib/**/*.js
client typed/transitional source -> lib/client.js
                                  -> lib/types/**/*.d.ts
```

The preferred artifact directory remains `lib`; introducing `dist` has no identified
architectural benefit. Ordinary generated Host JavaScript should not become a second
checked-in source of truth.

Host code remains unbundled ESM. Browser code is a separate build/type world.

## Type ownership

Use DSH package-exported public contracts wherever DSH owns the concept. DVR owns only
DVR semantics such as routing decisions, capability evidence, image ownership, Session
vision state, provider configuration, diagnostics, and resource ownership.

Do not create a generic `DvrContext`, Host facade, service locator, DI container,
global registry, or callback bag to make TypeScript conversion easier.

## Runtime validation

TypeScript never replaces validation at Settings/JSON, RPC, provider/network,
filesystem, persisted state, environment, browser/Node, or user-input boundaries.

Preferred rule:

```text
unknown -> boundary parser/official codec -> typed value -> domain
```

Schemastery remains the owner for plugin Config/Settings schema. Zod or another runtime
validator is justified only for complex untrusted external shapes; browser code should
not gain a heavyweight validator merely for type symmetry.

## Host / Client programs

Host and browser Client must be type-checked as separate programs. DSH itself separates
the two because both sides augment Cordis Context under different runtime contracts.

Host compilation should follow real Node ESM resolution rather than copying DSH's
monorepo-only build choices mechanically. Current target for the Host compiler is
NodeNext/NodeNext with explicit ESM extension discipline.

## Browser constraint

The existing `262144` byte single-file review bound for `lib/client.js` is frozen.
3.0 must not raise it to make TypeScript fit. Client migration is an independent Go/No-Go
workstream and may remain partly JavaScript if typed generation would weaken
determinism, debugging, loader transparency, or the size gate.

## Compatibility

Runtime Host compatibility and durable user-data compatibility are independent.

3.0 may raise the Host floor only after a dedicated evidence gate proves that the
removed Host generations account for real compatibility complexity. A higher Host floor
does not authorize deleting readers/migrations for persisted Settings, profile data,
Session/replay data, attachment identity, or historical image ownership.

No speculative DSH 0.3 implementation is part of this plan.

## Production dependency policy

Production runtime code may depend on documented/package-exported DSH faces. It must
not import `@deepseek-ai/*/src/*` or DeepSeek Harness monorepo filesystem internals.

Exact-source compatibility surveillance under `scripts/` and tests is a separate
category: it may inspect upstream implementation source to detect Host drift or a shim's
removal condition, but that source dependency must not enter runtime code, public
declarations, or the npm runtime graph.

## Public API direction

R7 replaced the former transitive mature-Core export graph with an explicit package-root
runtime/type surface. New Core exports no longer become package API automatically.

`./client` remains a DSH loader entry and is not treated as an ordinary consumer
library API.

The detailed final evidence and audit findings are recorded in
`docs/architecture/3.0-r9-final-audit.md`.

### R0 - Baseline and contract ledger

- freeze package/export/browser/support facts;
- record DSH public type authorities;
- classify current package-root exposure;
- gate production private DSH source imports;
- record compatibility candidates without deleting them.

### R1 - Source/artifact boundary

- establish `src` as canonical source and `lib` as generated output;
- preserve behavior/module ownership during relocation;
- add clean/reproducible artifact checks;
- do not combine source moves with semantic refactors.

### R2 - Type infrastructure and Host boundaries

- separate Host and Client TypeScript programs;
- add strict compiler policy;
- type Settings, Session, LLM/provider, attachment, RemoteResult, and composition inputs
  against DSH public contracts;
- allow a controlled JS bridge during migration.

### R3 - DVR domain types

Type only stable DVR-owned semantics. Do not create interfaces without a named owner and
a concrete coupling/risk they reduce.

### R4 - Composition and mature Core

Migrate composition/lifecycle before low-value algorithmic code. Mature Core conversion
is incremental and must not trigger decomposition solely for file size.

### R5 - Browser Client

Run an independent typed-source/build experiment. Switch production ownership only when
the output is deterministic, understandable, uses only supported runtime externals,
passes real browser/Desktop tests, and stays at or below 256 KiB.

### R6 - Compatibility retirement / Host floor

Re-run every shim's documented removal condition. Host-floor changes are evidence-based
and do not retire durable-data compatibility.

### R7 - Public API

Classify root exports as plugin contract, supported API, compatibility API, accidental
internal, or test-only. Publish only deliberate types/runtime faces.

### R8 - CI/release

Add typecheck, lint, clean build, generated sync, reproducibility, packed declaration
smoke, and source-to-artifact evidence without weakening the existing pack-once,
tarball-identity, trusted-publishing, and provenance model.

### R9 - Final audit

Re-run ownership, lifecycle, dependency-cycle, browser, compatibility, package,
Node 22/24, supported DSH, Desktop, adversarial, property, resource, and release audits.

## Explicit non-goals

- 100% TypeScript conversion;
- Big Bang rewrite;
- generic DI/service locator;
- global current owner or registry;
- `Object.create(core)` facade;
- Config/Settings impersonation;
- Core decomposition by LOC;
- composition splitting by fan-out;
- routing/Session/provider rewrites unrelated to a proven 3.0 seam;
- browser size-limit increase;
- importing DSH private implementation to obtain richer types;
- deleting runtime validation because code is typed.
